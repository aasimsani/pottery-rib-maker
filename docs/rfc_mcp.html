RFC-001 · Pottery tools · Draft · 2026-11-02

Each app's Cloudflare Worker hosts an MCP server that drives your open tab, so Claude can look at a design, change it and look again until it's right.

Claude reaches the tab through a live session that you start and approve in the tab. That costs a Durable Object, Turnstile and rate limits on each Worker, and it means no design code is copied, because the tab still does all the drawing. If the Worker session fails, a local server on 127.0.0.1 is the fallback.

01 · Problem and goal

Claude can't see or change a design in the apps, so it can't improve one on its own.

Goals

  • Claude reads the whole design, which is the settings, the layers, the print check and the sizes, in one call.
  • Claude changes settings and layers, adds library designs and local images, and the tab rebuilds as it does after a click.
  • Each round of changes, from one to many, comes back with the new preview image and the new print check, so Claude judges the result straight away.
  • Claude saves checkpoints, compares two of them side by side, and goes back to one, so an experiment never loses a good design.
  • MCP prompts teach Claude the loop and the design rules for each app, and one prompt writes an image-generator prompt sized to the live roller.
  • Claude exports the STL, the 3MF plate and the flat PNG.
  • Nobody can drive a tab you haven't opened and approved.

Non-goals

  • Running the apps without a browser. The drawing code needs a real canvas.
  • Storing designs on the server. They stay in your browser, as they do now.
  • Slicing or sending prints to the P2S.

04 · Chosen solution

You start a live session in the tab, Claude Code authorizes against it, and the Worker relays each tool call to the tab.

  • A wins because it works on aasimsani.net and in dev, renders with the app's own code, and keeps you watching every change.
  • B is the fallback, because it avoids a public endpoint. It loses as the main path because Chrome restricts the live site from reaching 127.0.0.1, so it only works against the dev server.
  • C loses because the art and library code would need a native canvas and a second copy of the sources, and you couldn't watch it.
  • D loses because every tweak takes several clicks and screenshots, and a renamed button breaks it.

The live session

  1. Connect Claude in the app's header
  2. Turnstile proves you're a person
  3. Session opens and the tab shows a code
  4. Claude Code signs in and opens the approval page
  5. You approve in the tab with the same code
  • A session lasts 2 hours, and it ends when you close the tab, press Disconnect, or leave it idle for 30 minutes.
  • A token only works for its own session, so closing the tab makes the token useless.
  • The tab shows a banner while Claude is connected, and each change Claude makes flashes in the panel it touched.

Trade-offs and caveats

  • The Worker becomes a public endpoint, so the abuse guards above have to ship with it.
  • Every tool call crosses the internet twice. A change still waits for the tab's rebuild, which takes about 4 s on the first roller build.
  • Screenshots cost tokens. Each one is scaled to at most 1200 px, which comes to about 1,500 tokens.
  • The roller needs its Worker and deploy pipeline before its MCP goes live.
  • Durable Objects and rate limits are new Cloudflare features on the account, which may cost money past the free tier.

05 · Build plan overview

Each Worker gains an MCP route, an approval page and a session object, and each tab gains a bridge.

new codethird partyunchanged

  1. A request reaches /mcp with a token.
  2. The Worker checks the token, then the per-token rate limit.
  3. A token whose session has ended gets 401, and Claude Code asks you to sign in again.
  4. A live token goes to its Session object, which forwards it to the one tab you approved.

The design_roller prompt, in outline
  1. Call get_state and view, and say what you see before you change anything.
  2. Fix errors first, then warnings, then looks.
  3. Save a checkpoint before each round. Change as many things as one idea needs, and send them together with batch, so they share one rebuild.
  4. Judge each preview against the rules: lines and gaps at least two nozzle widths, gaps at least as wide as the relief is deep, relief spread evenly round the turn, and no straight lines along the axle.
  5. Keep a round only when the check and the preview both get better. Otherwise restore.
  6. Stop when the check passes and the preview reads well, and ask you before you export.
Option B and option C in full

Option B runs node mcp/server.ts as a stdio MCP server, which opens a WebSocket on 127.0.0.1, and the tab dials it when its URL carries ?mcp. It needs no public endpoint and no sign-in, and it's the fallback. It loses as the main path because Chrome's Private Network Access rules restrict a public site's requests to local addresses, so it only works against the dev server.

Option C would import the pipeline into Node. Lines layers already work there, because src/core/lines.ts draws without a canvas. Every other layer goes through renderTile() and loadArt(), which need a canvas, image decoding and SVG rasterizing, so it means adding @napi-rs/canvas and keeping a Node copy of each source in step with the browser one.

Cross-cutting

  • Security. Claude only reaches a tab you opened, passed Turnstile in and approved. Tokens die with their session, and both rate limits cap what a stolen token could do.
  • Privacy. Designs, images and previews pass through the Worker in memory and aren't stored. The Session object keeps only its id, its expiry and the approved client.
  • Cost. The Worker relays small messages and never runs the pipeline. The open question on the free plan decides whether this costs anything.
  • Observability. The Worker logs each tool call's name, session and duration, never its contents, and Workers Logs keeps them.

Untouched. The pipelines, the Web Workers, the print checks, the mesh code and the static file routes stay as they are.
